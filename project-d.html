项目背景与价值

企业里「问数」是最高频、最刚需的数据动作，但 SQL 门槛把绝大多数业务/运营人员挡在门外： 取数要么排队等研发、要么在报表系统里反复点选，一条临时分析需求动辄 1–3 天。

本项目的目标：把「人写 SQL」变成「自然语言问数」——Agent 自动完成理解、生成、执行、校验、 回答，并保证只读安全、结果可审计，让非技术员工直接自助取数。

核心问题（本实验要回答的）：多 Agent 架构比单 Agent 强在哪？强多少？代价是什么？ 这需要一套能排除干扰变量的评测方法——见下方「消融设计」。

双架构对比（实验设计）

维度对照组 · 单 Agent 基线实验组 · 多 Agent 流水线
结构一个 LLM 三合一：理解 + 生成 SQL + 自查五段流水线：语义理解 → SQL 生成 → 清洗 → 执行 → 质检&解释
模型完全一致：DeepSeek V4.1 Flash（deepseek-flash）
平台完全一致：Dify 本地容器（私有化部署）
评测题集完全一致：同一 39 题分层评测集（Spider-car_1 库）
差异点仅此一个变量：架构职责分离 + 格式清洗 + 质检兜底
消融设计说明：两套应用用同一个模型（DeepSeek V4.1 Flash）、同一个平台（Dify）、同一份 39 题， 唯一区别是 Agent 编排架构。这样所有指标差异都来自「架构」，不被「模型能力差异」污染—— 这正弥补了三平台评测（作品 1）里「三平台用三个模型、分数混杂模型效应」的局限。

多 Agent 五段流水线（每段职责）

节点职责产出为什么需要
① 语义理解 Agent解析用户意图意图 JSON（tables / target / filters / agg）把口语翻译成「查询意图」，不给写 SQL 的 Agent 留歧义
② SQL 生成 Agent只写 SQLSELECT 开头的 SQLprompt 极聚焦，不干别的活
③ 清洗节点（code）格式兜底纯 SQL（剥 think 块 / Markdown 标记）推理模型会吐思考内容污染 SQL → 执行率 100% 的关键
④ SQL 执行工具沙箱执行结果行集SQLite 只读（mode=ro + query_only + 仅 SELECT/WITH + 200 行上限 + 超时）→ ToB 数据安全底线
⑤ 质检&解释 Agent校验 + 人话回答qa_pass 判定 + 自然语言答案拦截错误输出（15.4%）、让答案可审计

评测方法学（Spider 官方口径）

数据集Spider —— NL2SQL 领域公认最难基准（166 库 / 1034 题），本项目取 car_1 汽车经销商库（6 表 / 406 辆车）。

评测集39 题分层抽样（easy 4 / medium 20 / hard 15，随机种子 42），每题带官方 golden SQL 与预计算结果。

双口径严格口径 = Spider 官方 execution accuracy：执行生成的 SQL，结果行集与 golden 逐行比对，多一列 / 少一列 / 多一行重复都算错； 业务口径 = 结果按 golden 列投影后包含全部信息（多查一列容忍）——严谨性与业务价值兼顾。

六指标SQL 可执行率 · 端到端达成率（严格）· 业务可达率 · 质检拦截率 · 平均耗时 · 平均 Token 成本。

核心结果：多 Agent 全面胜出（除延迟）

指标单 Agent 基线多 Agent 流水线变化
SQL 可执行率84.6%100%+15.4pp
端到端达成率（严格口径）35.9%66.7%+30.8pp
业务可达率（宽松口径）43.6%66.7%+23.1pp
质检拦截率（多 Agent 特有）—15.4%（6/39）安全兜底
平均耗时6.07s8.95s+47%（代价）
平均 Token 成本39962878−28%（反降）

trade-off 结论：多 Agent 用「+2.9s 延迟」换「准确率近翻倍 + 成本反降 28%」——因为分段 prompt 聚焦、失败重试更少。 这正是面试/售前里多 Agent 架构权衡的标准答案。

分难度提升：架构收益集中在中等复杂度

难度题数单 Agent多 Agent变化
easy450%50%持平
medium2035%85%+50pp（最大增益）
hard1533.3%46.7%+13.4pp

洞察：架构优化在「中等复杂度」查询上收益最大（多表 JOIN、分组、聚合）——轻量模型打不过复杂查询时， 「用工程补模型」的证据。简单题两种架构都能答，极难题是模型能力边界，工程也救不了。

逐题消融矩阵（39 题逐题比对）

分组（严格口径）题数解读
双双都对11简单/中等题，两架构都能答
单错 → 多对（多 Agent 救回）1512 medium + 3 hard —— 职责分离的直接收益
单对 → 多错（多 Agent 退步）31 medium + 2 hard —— 链路损耗与质检误报的诚实暴露
双双都错102 easy（golden 缺失）+ 2 medium + 6 hard —— 模型能力边界

多 Agent 净救回 12 题（15 − 3），且救回的全是「中等偏难」题——这是把「架构值多少钱」讲成数字的证据。

失败归因：工程问题 vs 模型问题

失败阶段单 Agent（25 失败）多 Agent（13 失败）
SQL 执行失败6 题（think 块污染、方言残留）0 题（清洗节点兜底）
严格口径结果不匹配16 题13 题（全为 JOIN / 子查询 / NOT EXISTS 场景：漏 DISTINCT、列选择差异）
多余列（业务口径可命中）3 题（多查 COUNT 列等）0 题（质检要求精确输出）
评测集缺陷2 题 easy 的官方 golden 为空（数据缺失，非模型问题）

诊断结论：多 Agent 解决「工程问题」（格式污染、输出失控），解决不了「模型理解问题」（复杂查询语义歧义）——清晰的边界认知。

亮点案例（hard 题成功，模型 × 工程协同）

题："How many cars have a larger accelerate than the car with the largest horsepower?"

SELECT COUNT(*) FROM cars_data WHERE Accelerate > (SELECT Accelerate FROM cars_data ORDER BY Horsepower DESC LIMIT 1);

子查询 + 排序取极值，语义完全正确 —— 轻量模型在「语义层 prompt（表结构 + 口径规则）」引导下能写出复杂 SQL。

题："What are the name of the countries where there is not a car maker?"

SELECT CountryName FROM countries WHERE NOT EXISTS (SELECT 1 FROM car_makers WHERE car_makers.Country = countries.CountryId);

工程攻坚（真实踩坑 6 例）

  • Dify 编排页不保存 prompt：contenteditable 编辑器 JS 填充 / execCommand 均不触发自动保存 → 弃 UI，直改 Postgres（app_model_configs.pre_prompt / agent_mode 列）注入配置。
  • 工具 provider_id 必须用 DB UUID：填名字会让应用 GET 500 → 从 tool_api_providers 表取真实 UUID 写入。
  • Chatflow 发布需显式调接口：POST /console/api/apps/{id}/workflows/publish，否则调用报 "Workflow not published"。
  • 流式事件名差异：节点事件是 node_finished 而非 workflow_node_executed，评测采集踩坑后修正。
  • 执行服务返回字符串行：如 "(1970,)"，评测脚本需 ast.literal_eval 解析，否则全量误判。
  • 安全沙箱：SQLite 只读 mode=ro + PRAGMA query_only + 仅 SELECT/WITH 前缀 + 200 行上限 + 超时 —— 问数场景的数据安全底线。

成果衡量与诚实声明

北极星指标：端到端达成率（严格口径）= 执行 Agent 生成的 SQL，结果与 golden SQL 结果完全一致才算对。多 Agent 66.7% vs 单 Agent 35.9%。

诚实声明：① 评测为 car_1 单库 39 题子集，非 Spider 官方全量 1034 题测试集，数字不直接对标官方 leaderboard；② 39 题中 2 题官方 golden 缺失，剔除后有效 37 题 → 单 Agent 37.8%、多 Agent 70.3%（两种口径均已披露）；③ 严格口径「多一列都算错」，属 Spider 官方严苛判定，数字天然偏低；④ 模型为 DeepSeek V4.1 Flash（轻量版），若换旗舰模型数字会更高，但消融结论（架构差异）不变。
